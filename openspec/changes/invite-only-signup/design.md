## Context

Учётку сейчас заводят три места, все через `usersService.findOrCreateByTelegramId` (`server/src/modules/users/users.service.ts`):

- `POST /auth/telegram-webapp` и `POST /auth/telegram-login` в `server/src/modules/auth/auth.routes.ts`;
- `resolveAuthUser` (`server/src/modules/auth/resolve-auth-user.ts`) — разбор заголовка `X-Telegram-Init-Data` на **каждом** GraphQL-запросе из Mini App.

Telegram здесь — только бот (`tg` в `server/src/mtcute/index.ts`, `Dispatcher` на bot token). User-сеанс `tgAdmin` к приглашениям не относится. Mini App и виджет приходят на HTTP API, не в бот.

Права — матрица в `server/src/modules/auth/permissions.ts`, проверка в боте — `assertPermission` (`mtcute/guards/assert-admin.ts`). Сессии хранят только sha256 токена (`session.service.ts`) — тот же приём подходит коду приглашения.

На проде счётчик `Users.id` стоял на 1 при существующей строке `id = 1` (владельца вставили с явным id): первая новая учётка падала с `duplicate key`. 9.11 его выровняли вручную; миграции нет.

`SITE_URL` на сервере — домен без `/essence` (он же источник CORS в `config/cors.ts`), поэтому кнопка `/app` (`mtcute/commands/index.ts`, `BotKeyboard.url('Запустить', https://${SITE_URL}/)`) ведёт на лендинг, а не в каталог.

## Goals / Non-Goals

**Goals:**

- Ни один HTTP-вход не заводит учётку; заводит только бот при активации приглашения (и владелец из `BOT_ADMIN_ID` — при первом входе, как сейчас).
- Код приглашения не лежит в базе в открытом виде.
- Отказ «Доступ по приглашению» доходит до экрана входа текстом, без новых экранов.

**Non-Goals:**

- Новый контракт GraphQL: приглашения живут в боте, API их не видит.
- Общий модуль «пользовательских команд бота» — две команды и deeplink пишутся рядом с `channel.ts` в том же стиле.

## Decisions

### Код и ссылка

Код — 24 байта `randomBytes` в base64url (32 символа, в пределах 64 допустимых для `start`-параметра). В базе — sha256 кода, как у сессий. Ссылка `https://t.me/<бот>?start=inv_<код>`; имя бота берём из `tg.getMe()` при старте, не из env.

*Альтернатива:* короткий человекочитаемый код (`ABCD-1234`). Отвергнута: перебор по сети тривиален, а вводить его руками не нужно — ссылка открывается тапом.

### Таблица `Invite`

`id`, `codeHash @unique`, `createdById → Users`, `createdAt`, `expiresAt`, `usedById → Users?`, `usedAt?`, `revokedAt?`. Действующее = `usedAt IS NULL AND revokedAt IS NULL AND expiresAt > now()`.

Активация — один `updateMany` с этим условием и `where codeHash`: если `count = 0`, приглашение недействительно (гонка двух аккаунтов на одну ссылку решается самой базой, второй получает отказ). Учётка и отметка `usedById` — в одной транзакции.

*Альтернатива:* флаг `isInvited` у `Users` и allowlist Telegram id. Отвергнута: автору пришлось бы узнавать числовой id друга.

### Вход без заведения учётки

`findOrCreateByTelegramId` заменяется на `findForLogin(telegramId, username)`: находит учётку и обновляет username как сейчас; если учётки нет — создаёт **только** для `BOT_ADMIN_ID` (роль `OWNER`), иначе возвращает `null`. Создание по приглашению — отдельный метод `createFromInvite` внутри транзакции активации.

Ответ HTTP для незнакомого аккаунта — `403 { error: 'Доступ по приглашению' }` на обоих `/auth/*`. `resolveAuthUser` в этом случае возвращает `null` — GraphQL отвечает обычным 401. Клиенту отдельный код не нужен: `LoginScreen` уже показывает `error` из ответа входа; добавляется только подсказка под текстом.

*Альтернатива:* 401 для незнакомого. Отвергнута: экран входа не отличил бы «нет приглашения» от «подпись протухла».

### Команды бота

- `/invite` — по праву `users:invite`: создаёт приглашение, отвечает ссылкой и сроком.
- `/invites` — список действующих приглашений автора с кнопкой «Отозвать» у каждого (callback по `id`, проверка, что приглашение создал тот же пользователь или у него `OWNER`).
- `/start inv_<код>` через `filters.deeplink(/^inv_/)` — активация; без права, это вход нового человека. Ответ — кнопка `BotKeyboard.webView('Открыть каталог', <адрес каталога>)`, чтобы каталог открылся как Mini App и вошёл молча по `initData`.
- Команды попадают в `setMyCommands`.

Адрес каталога собирается одной функцией `https://${SITE_URL}/essence/`; ей же переводится кнопка `/app`, сейчас ведущая на лендинг.

### Срок

7 дней константой в коде. Отдельная env-переменная не нужна, пока срок никто не просил менять.

### Счётчик id

В миграции с таблицей `Invite`: `SELECT setval(pg_get_serial_sequence('"Users"','id'), GREATEST((SELECT MAX(id) FROM "Users"), 1))`. На проде — no-op (уже выровнен), локально и на свежих базах — защита.

## Risks / Trade-offs

- [Ссылку переслали дальше, и первым её открыл не тот человек] → одноразовость + отзыв в `/invites`; удаление лишней учётки пока руками в базе (non-goal proposal).
- [Друг открыл каталог раньше, чем ссылку] → увидит «Доступ по приглашению» с подсказкой; после активации уже открытый Mini App сам не пустит — вход заново через кнопку «Открыть каталог» из ответа бота.
- [`resolveAuthUser` на каждом GraphQL-запросе Mini App больше не создаёт учётку] → незнакомый аккаунт получает 401 на всё, клиент уходит на экран входа по существующему `AUTH_SIGNED_OUT_EVENT`.
- [Код в Telegram-ссылке виден в истории чата друга] → он одноразовый, после активации бесполезен.

## Migration Plan

1. Миграция Prisma: таблица `Invite` + выравнивание счётчика `Users.id`.
2. Деплой backend и бота вместе (один образ). До деплоя бота ссылки не создаются, так что порядок внутри одного деплоя не важен.
3. Откат: откатить образ; таблица `Invite` старому коду не мешает. Учётки, созданные по приглашениям, остаются рабочими и после отката.
