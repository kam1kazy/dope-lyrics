## Context

См. proposal.md — Why.

Что есть сейчас и что этим ограничивает:

- `Lyrics.userId` в схеме есть, но пишется всегда `owner.id` (`usersService.ensureOwner`, пользователь 1), а на чтение по владельцу не фильтрует никто — в `lyrics-list-filters.ts` условия по владельцу нет.
- `LyricCollage` и `CarouselHistory` владельца не имеют вовсе: история карусели и лайкнутые склейки общие на базу.
- `Users` — заглушка: `username`, `email`, `password` (пароль лежит открытым текстом у сидового `owner`), связи с Telegram нет.
- Дедуп ingest — пара `(source, lyric_id)`, где `lyric_id` = `message_id` Telegram. Индекс `@@index([source, lyric_id])` глобальный.
- Вход в production — `securityPlugin.onBeforeHandle`: `X-Telegram-Init-Data` проверяется и сверяется с `telegramAdminId`. Контекст GraphQL (`createContext`) несёт только `prisma`.
- Историю канала читает `tgAdmin` — MTProto-сессия личного аккаунта владельца (`BOT_PHONE`, 2FA). Бот такого не умеет.

## Goals / Non-Goals

**Goals**

- Изоляция по владельцу в одной точке, а не проверкой в каждом резолвере.
- Вход по Telegram-аккаунту, работающий и в Mini App, и в браузере/PWA.
- Приём постов из канала друга без доступа к его Telegram-аккаунту.

**Non-Goals** (сверх proposal)

- Не переносим Express-middleware youways как есть: стек другой (Elysia + Yoga). Копируем модель сессии, обвязку пишем под Elysia.
- Не разносим данные по схемам/базам на пользователя. Одна база, колонка владельца.
- Не трогаем формулы готовности, профиля, генератора и карусели — только область видимости.

## Decisions

### 1. Владелец — колонка, изоляция — в одной точке

`Lyrics.userId` начинаем использовать по-настоящему; `LyricCollage` и `CarouselHistory` получают такую же колонку и индекс по `(userId, createdAt)`.

Ключевое: фильтр владельца ставится **внутри слоя выборки** (`buildLyricsWhere` и парные сборщики `where` в `lyrics.service.ts`), а `userId` приходит из контекста GraphQL, не из аргументов запроса. Клиент не может попросить чужой каталог, потому что такого аргумента нет.

Альтернативы: проверка в каждом резолвере — отвергнута, забудешь один из ~40 и получишь утечку; Postgres RLS — честнее, но требует прокидывать роль/`SET LOCAL` через Prisma на каждый запрос, для одного инстанса это лишняя механика.

Мутации над конкретной записью проверяют владельца в самом `UPDATE`/`DELETE` (`where: { id, userId }`), а не отдельным `SELECT` перед ним: нет гонки и нет второго запроса. Ноль затронутых строк → ошибка «не найдено» по-русски, одинаковая для чужой и несуществующей записи.

### 2. Дедуп становится трёхсоставным

Было `(source, lyric_id)`, станет `(userId, source, lyric_id)` — уникальный индекс, а не просто индекс. Иначе пост №42 в канале друга схлопнется с вашим №42: `lyric_id` уникален внутри чата, а не глобально.

Записи без Telegram-происхождения (склейка ставит `lyric_id = 0`) в уникальный индекс не влезут — их несколько на пользователя. Поэтому индекс делаем частичным: только для строк с `lyric_id > 0`.

### 3. `Users` привязывается к Telegram, пароль уходит

Добавляем `telegramId BigInt @unique` и `role` (`ADMIN` | `USER`). `email` и `password` становятся необязательными и в новом контуре не заполняются — иначе придётся тащить bcrypt ради поля, которым никто не пользуется. Существующий `owner` (id 1) получает `telegramId` из `BOT_ADMIN_ID` и роль `ADMIN`, чтобы ваш каталог не отвязался.

### 4. Два входа, одна сессия

Проверка на сервере разная, результат один — запись в таблице сессий и httpOnly cookie:

- **Mini App**: `initData`, HMAC с ключом `HMAC(WebAppData, botToken)` — уже реализовано в `verifyTelegramWebAppUserId`, переиспользуем.
- **Браузер/PWA**: Telegram Login Widget, у него **другая** схема — ключ `SHA256(botToken)`, поля приходят из `?hash=…`. Это отдельная функция проверки, не переиспользование первой; перепутать ключи легко, поэтому держим их рядом с тестами.

Сессия — случайный непредсказуемый токен в БД (не самоподписанный JWT): так выход и отзыв работают сразу, что для «дал друзьям попользоваться» важнее, чем экономия запроса. Refresh с ротацией — как в youways.

### 5. В Mini App остаётся заголовок, cookie — для браузера

В WebView Telegram cookie на вашем домене легко попадают под блокировку сторонних cookie (особенно iOS/Safari). Поэтому Mini App продолжает ходить с `X-Telegram-Init-Data`, а cookie-сессия — контур браузера и PWA. `securityPlugin` пускает запрос, если **любой** из двух контуров дал пользователя.

Альтернатива «везде только cookie» отвергнута: рискуем сломать рабочий Mini App ради единообразия.

### 6. Канал друга: бот-участник, привязка с проверкой прав

Пользователь добавляет бота в свой канал, затем привязывает канал командой. Бот проверяет через Telegram, что этот пользователь — владелец или администратор канала; иначе привязки нет. Привязка — отдельная таблица «канал → пользователь», уникальная по каналу.

Новые посты приходят боту как обновления канала и пишутся владельцу привязки. История не подтягивается: бот в Telegram не может прочитать прошлые сообщения. Просить у друга телефон и код, чтобы поднять MTProto-сессию как у админа, мы не будем — это полный доступ к его аккаунту.

Ваш собственный контур (`tgAdmin` + `BOT_CHANNEL_ID` + кнопка «Парсинг чата» в `/bd`) остаётся как есть, админский, и пишет в ваш каталог.

### 7. Состояние бота — по отправителю

Ожидания `/notes` (путь к папке, окно приёма zip) сейчас хранятся под одного админа. Ключом становится Telegram user id отправителя, иначе двое одновременно перетрут настройки друг друга.

Команды бота требуют заведённой учётки: если человек не входил в каталог, `/notes` отвечает по-русски, что сначала нужно открыть приложение.

## Risks / Trade-offs

- **Забытый фильтр владельца в одной из выборок → чужие тексты в каталоге.** → Единая точка сборки `where` вместо проверок по резолверам; тест «автор B не видит фразы автора A» на список, карусель, сводку, историю и склейки.
- **Cookie не доезжают в WebView Telegram.** → Mini App не переводим на cookie, оставляем заголовок `initData`.
- **Уникальный индекс `(userId, source, lyric_id)` не встанет из-за существующих дублей.** → Перед миграцией посчитать дубли в текущей базе; при находках чинить данные, а не ослаблять индекс.
- **Друг ждёт, что бот подтянет его историю.** → Предупреждение при привязке и в FAQ; путь для истории — экспорт заметок Apple Notes, который уже работает.
- **Разрастание базы от чужих корпусов.** → Пока круг друзей, лимитов не вводим; если понадобится — квота на пользователя отдельным изменением.
- **`BOT_ADMIN_ID` больше не единственный пропуск: ошибка в проверке сессии открывает каталог наружу.** → Отказ по умолчанию: нет пользователя в контексте — нет доступа; локальный `NODE_ENV=development` по-прежнему не включает проверку.

## Migration Plan

1. Колонки владельца добавляются **nullable**: `LyricCollage.userId`, `CarouselHistory.userId`; `Users.telegramId`, `Users.role`.
2. Бэкфилл: всё существующее (`Lyrics`, `LyricCollage`, `CarouselHistory`) — на пользователя 1; ему же `telegramId` из `BOT_ADMIN_ID` и роль `ADMIN`.
3. Колонки переводятся в `NOT NULL`; старый индекс `(source, lyric_id)` заменяется на частичный уникальный `(userId, source, lyric_id)` при `lyric_id > 0`.
4. Сервер выкатывается с двумя контурами входа сразу: Mini App продолжает работать без пауз.
5. Друзей пускаем последним шагом, после проверки изоляции на двух живых учётках.

Откат: шаги 1–3 обратимы (снять `NOT NULL`, вернуть индекс); данные при откате не теряются, потому что колонки только добавлялись. Сидовый `owner` с открытым паролем удаляется отдельно — не в этой миграции, чтобы откат не остался без владельца.
