## Purpose

Роли и права отделяют владельца платформы, помощника и обычного автора. Операция проверяется правом из матрицы в коде; экранов управления ролями нет — роль меняется в базе.

## ADDED Requirements

### Requirement: Набор ролей

Система MUST хранить у учётки одну роль из набора `OWNER`, `ADMIN`, `USER`. Новая учётка MUST получать роль `USER`. Роль MUST NOT выводиться из Telegram-аккаунта при каждом запросе, кроме первичного назначения `OWNER` из `BOT_ADMIN_ID` при миграции и первом входе владельца.

Изоляция каталога по владельцу MUST оставаться независимой от роли: `ADMIN` и `OWNER` MUST NOT видеть чужие тексты в обычных выборках каталога. Роль даёт доступ к операциям, а не к чужому корпусу.

#### Scenario: Новый друг — USER

- **WHEN** новый Telegram-аккаунт входит впервые
- **THEN** учётка заводится с ролью `USER`

#### Scenario: Админ не видит чужой каталог

- **GIVEN** у автора A есть фразы, у `ADMIN` — свои
- **WHEN** `ADMIN` открывает каталог
- **THEN** он видит только свои фразы, фразы автора A не отдаются

### Requirement: Операция проверяется правом

Система MUST проверять доступ к операции по праву, а не сравнением роли со строкой в месте вызова. Набор прав первого контура MUST включать как минимум: `db:seed`, `db:clear`, `db:parse`, `users:list`, `users:role`, `catalog:own`, `channel:bind`, `notes:import`.

Права роли:

- `USER` — `catalog:own`, `channel:bind`, `notes:import`.
- `ADMIN` — права `USER` плюс `users:list` (и позже другие неразрушающие операции управления).
- `OWNER` — все права, включая `db:seed`, `db:clear`, `db:parse`, `users:role`.

Неизвестное право MUST считаться запрещённым. Отказ MUST быть по-русски и MUST NOT менять данные.

#### Scenario: USER не чистит базу

- **GIVEN** вошёл пользователь с ролью `USER`
- **WHEN** он вызывает очистку базы
- **THEN** система отказывает по-русски и ничего не меняет в базе

#### Scenario: ADMIN не выполняет разрушающие операции

- **GIVEN** вошёл пользователь с ролью `ADMIN`
- **WHEN** он вызывает посев, парсинг канала владельца или очистку базы
- **THEN** система отказывает по-русски и ничего не меняет

#### Scenario: OWNER управляет базой

- **GIVEN** вошёл пользователь с ролью `OWNER`
- **WHEN** он вызывает команду управления базой с правом `db:*`
- **THEN** операция выполняется

#### Scenario: Неизвестное право запрещено

- **GIVEN** в коде запрошено право, которого нет в матрице
- **WHEN** проверяется доступ
- **THEN** доступ запрещён

### Requirement: OWNER из BOT_ADMIN_ID

Миграция MUST назначить роль `OWNER` учётке с `telegramId` из `BOT_ADMIN_ID` (существующий владелец каталога). Система MUST NOT оставаться без хотя бы одной учётки с ролью `OWNER` после миграции.

Смена ролей в этом изменении MUST выполняться только правкой в базе (или скриптом), не из UI приложения.

#### Scenario: После миграции есть OWNER

- **GIVEN** в `.env` задан `BOT_ADMIN_ID` и в базе есть владелец каталога
- **WHEN** применена миграция
- **THEN** у этой учётки роль `OWNER` и привязанный Telegram id
