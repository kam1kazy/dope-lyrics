# ADR 0009 — Учётка, сессия и роли вместо только Mini App

Статус: принято
Дата: 2026-09-07
Отменяет: [0007](./0007-mini-app-initdata.md)

## Решение

1. Учётка привязана к Telegram-аккаунту, пароля нет. **С 2026-11-09 — только по приглашению:** `/invite` в боте (право `users:invite`) даёт одноразовую ссылку на 7 дней, бот заводит учётку при `/start inv_…`. Вход из Mini App и виджетом учётку не заводит (кроме владельца из `BOT_ADMIN_ID`), незнакомому — 403 «Доступ по приглашению».
2. Сессия — httpOnly cookie (`dl_session`) с записью в БД и refresh; GraphQL в production пускает по сессии **или** по `initData`.
3. Роли `OWNER` | `ADMIN` | `USER`; права — матрица в `permissions.ts` через `can()`. UI управления ролями нет.
4. Каталог личный: все выборки и мутации с `userId` владельца. `BOT_ADMIN_ID` → роль `OWNER` при миграции, не единственный пропуск.

## Почему

Друзьям нужен свой корпус и вход вне чата (PWA). Один `BOT_ADMIN_ID` это ломает. Cookie youways-модель без tenant; Mini App не переводим целиком на cookie из‑за WebView.

## Отличие от youways

- **Одна серверная сессия, не пара access JWT + refresh.** Токен `dl_session` случайный, в БД только sha256. Каждый запрос всё равно идёт в базу (сессия или `initData`), а сокетов и tenant, ради которых в youways короткий JWT, здесь нет. Отзыв мгновенный.
- **Скользящий срок.** Клиент при старте зовёт `/auth/refresh`: токен ротируется, срок снова 30 дней. Между вкладками — `navigator.locks`, иначе вторая вкладка придёт с уже отозванным токеном.
- **CSRF как в youways.** POST на `/auth/*` — только JSON или `X-Requested-With`, плюс общая проверка Origin. `SameSite=Lax` не спасает от login CSRF через форму.
- **Детект повторного refresh не делаем.** В youways он фактически не срабатывает (старый токен удаляется, а не помечается). Повтор старого токена здесь просто даёт 401.
